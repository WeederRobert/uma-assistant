# 卡池与活动排期：数据结构、抽卡成本与跨服节奏

> **来源**：S10 本机客户端 `master.mdb`（卡池与剧情活动结构、成本与兑换列）+ S8/S11 BWiki `简中卡池` 页（预测卡池表）
> **来源版本**：S10 `mdb-cn-20261027`；S11 抓取时间 2026-11-01
> **抓取时间**：2026-11-01
> **可信级别**：A（mdb 结构与列）/ C（BWiki 的简中预测时间，是社区推算，且实测偏晚）
> **适用版本**：简中服
> **已知缺口**：不含任何当期卡池与活动日期（时效数据不写入本目录）；「抽卡点数如何累积」没有可核对来源

本目录其它篇讲**游戏机制**；这一篇讲**排期与规划的数据怎么读**。
「现在开到哪一期」属于时效信息，只在 `planner` / `gacha` 模块里展示，不进本目录。

## 卡池与剧情活动在客户端数据里的样子

| 表 | 内容 | 用途 |
| --- | --- | --- |
| `gacha_data` | 卡池：`start_date` / `end_date`（unix 秒）、`type` / `card_type`、`cost_single` | 排期与单抽成本 |
| `text_data`（26 / 13） | 卡池名称与说明 | 面板显示 |
| `gacha_available` | 池内所有卡与出率，`is_pickup = 1` 为精选 | Up 对象、与其他来源对齐 |
| `gacha_exchange` | `pay_item_num`：兑换本期 Up 卡需要的点数 | 天井口径 |
| `gacha_stepup` | 阶段池的步骤 → 子卡池映射 | 多阶段池（每步价格不同） |
| `gacha_free_campaign` | 免费抽的起止时间 | 免费抽窗口 |
| `story_event_data` | **剧情活动**：`notice_date` / `start_date` / `middle_date_*` / `ending_date` / `end_date` | 剧情活动排期（简中服节奏） |
| `text_data`（214 / 189） | 剧情活动名称（214 短名、189 长名） | 面板显示 |

两个要点：

- **剧情活动不需要跨服换算**：`story_event_data` 存的就是本客户端（简中服）的时间，
  和 `gacha_data` 一样可以当作简中服的实际排期（A 级）。
- **`gacha_data.type` 没有字典表**，只能回显原始编号；`card_type` 可以靠「能否 JOIN 到
  `card_data` / `support_card_data`」判定为马娘（1）/ 协助卡（2）。

## 成本与天井：能算的部分与算不了的部分

| 数 | 从哪来 | 能不能直接信 |
| --- | --- | --- |
| 单抽成本 150 | `gacha_data.cost_single` | 是主数据列，A 级 |
| 兑换 Up 卡需要的点数 200 | `gacha_exchange.pay_item_num` | 是主数据列，A 级 |
| 天井萝卜 = 200 × 150 = 30000 | 上两列相乘 | **「1 抽 = 1 点」这条换算规则不在 mdb 里**，属于推导，按 C 级理解 |

因此「天井要 30000 萝卜」是**两列真实数据 + 一条没有来源的换算**，回答时要写明这个前提，
不要当成官方公示的价格。

阶段池（`gacha_stepup`）每步价格不同：实测同一组阶段池的 `cost_single` 从 50 到 150 递增，
「阶段池第 N 步多少钱」只能按 `stepup_step` 逐条回显，不能用统一单价乘。

## 跨服节奏：简中服在加速，日服时间对不上轴

简中服进度晚于日服，但**不是固定间隔地晚**：内容在加速推进，间隔越缩越短。
用同一张精选角色把「mdb 实际开池日」与「BWiki 预测日」对齐，可以量出 wiki 偏晚多少：

> 截至 2026-11-01 实测 6 组配对：wiki 偏晚 **+35 天 → +55 天**，随日服日期递增
> （按时间顺序：35 / 40 / 44 / 44 / 50 / 55 天）。
> 这个数字随时效变化，以 `planner` 模块每次刷新的实测值为准，本目录不把它写成长期事实。

由此得到三条结论：

1. **不能用「日服 + 常数」换算**。wiki 页面上记着的 −185 / +72 / +423 / +21 天是历史调整账，
   只能说明「偏移一直在变」，不能当常数用。
2. **活动不能靠对轴**。简中服的活动顺序与日服并不一致（有的提前、有的合并、复刻还会推迟），
   从日服活动表换算出来的日期没有意义。剧情活动直接读 `story_event_data`。
3. **卡池预测可以校正，但仍然只是估计**。平移量要取最近一次实测偏差（偏差在不断变大，
   用早期的小偏差或整段中位数都会校正不足），并且必须把 `min~max` 区间和 wiki 原值一起给出。

## 做规划时的三条口径

1. **收入只能自己填**：主数据里没有任何「每月能攒多少萝卜」的表，活动与大赛产出也没有可靠官方数值，
   所以规划只做「你告诉我月收入，我按天折算」这一步，不内置估算。
2. **mdb 优先**：客户端内置排期（A 级）比任何社区推算可靠；两者的重叠段只用来量偏差，
   不参与消耗计算，避免同一期被算两次。
3. **买不起就记缺口，不扣账**：规划是「站队」而不是模拟真实抽卡，买不起的目标视为放弃，
   把资源留给后面的池子。
