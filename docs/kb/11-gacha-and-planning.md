# 卡池排期与抽卡规划：天井、成本、跨服节奏

> **来源**：S10 本机客户端 `master.mdb`（卡池结构、成本与兑换列）+ S8 BWiki `简中卡池` 页面（预测卡池表与跨服偏移）
> **来源版本**：S10 `mdb-cn-20261027`；S8 页面 `简中卡池` revid 见 3.2
> **抓取时间**：2026-11-01
> **可信级别**：A（mdb 结构与列）/ C（BWiki 的简中预测时间与偏移记录）
> **适用版本**：简中服
> **已知缺口**：不含任何当期卡池日期（时效数据不写入本目录）；「点数如何累积」的规则没有可核对来源

本目录其它篇讲的是**游戏机制**；这一篇讲**卡池数据怎么说、以及怎么用这些数据做规划**。
具体的「现在开到哪一期」属于时效信息，只在 `planner` / `gacha` 模块里展示，不进本目录。

## 卡池在客户端数据里的样子

`master.mdb` 把卡池写在 `gacha_data`，一条一行，含 `start_date` / `end_date`（unix 秒）与
`type` / `card_type`。配套的表：

| 表 | 内容 | 用途 |
| --- | --- | --- |
| `text_data`（26 / 13） | 卡池名称与说明 | 面板显示 |
| `gacha_available` | 池内所有卡与出率，`is_pickup = 1` 为精选 | 看这一期 Up 谁 |
| `gacha_exchange` | 兑换本期 Up 卡需要的点数（`pay_item_num`） | 天井口径 |
| `gacha_stepup` | 阶段池的步骤 → 子卡池映射 | 多阶段池（每步价格不同） |
| `gacha_free_campaign` | 免费抽的起止时间 | 免费抽窗口 |
| `gacha_data.cost_single` | 单抽成本 | 萝卜消耗 |

`gacha_data.type` **没有字典表**，只能回显原始编号；`card_type` 可以靠「能否 JOIN 到
`card_data` / `support_card_data`」判定为马娘（1）/ 协助卡（2）。

## 成本与天井：能算的部分与算不了的部分

| 数 | 从哪来 | 能不能直接信 |
| --- | --- | --- |
| 单抽成本 150 | `gacha_data.cost_single` | 是主数据列，A 级 |
| 兑换 Up 卡需要的点数 200 | `gacha_exchange.pay_item_num` | 是主数据列，A 级 |
| 天井萝卜 = 200 × 150 = 30000 | 上两列相乘 | **「1 抽 = 1 点」这条换算规则不在 mdb 里**，属于推导，按 C 级理解 |

因此「天井要 30000 萝卜」这个结论是**两列真实数据 + 一条没有来源的换算**，回答时要写明这个前提，
不要当成官方公示的「天井价格」。

阶段池（`gacha_stepup`）每步价格不同：实测同一组阶段池的 `cost_single` 从 50 到 150 递增，
所以「阶段池第 N 步多少钱」只能按 `gacha_stepup.stepup_step` 逐条回显，不能用统一单价乘。

## 跨服节奏与「千里眼」怎么来的

简中服进度晚于日服，因此**日服已经发生的事情就是简中服的未来**。BWiki 的 `简中卡池` 页面把这件事做成了数据：

1. 页面「预测卡池」表用 SMW 查询 `[[分类:赛马娘卡池]][[简中::未实装]]`，即「日服已上线、简中未实装」的卡池；
2. 每条卡池页面同时带**简中** `简中开始时间` / `简中结束时间` 与**日服** `开始描述`；
3. 两条相减就是该时间点的跨服偏移；偏移在相邻两点之间可按日服时间线性插值。

页面本身还记着几次调整（简中卡池加速 −185 天、2025/09/16 起 −72 天、2025/05/22 重新更新 +423 天、
2024/03/10 复刻推迟 +21 天）。这些是**历史账**，不能当常数用——简中服一旦再次追进度，写死的数字就错了。
正确做法是每次抓取都重新算。

> 截至 2026-11-01，本项目实测 136 组卡池的偏移完全一致（1104 天）。该数字随时效变化，
> 以 `planner` 模块每次刷新的实测值为准；本目录不把它写成长期事实。

活动同理：BWiki 的 `活动` 表只有日服时间（`开始描述` / `结束描述` / `类型`），没有简中属性。
要让活动出现在简中日程里，只能靠「同名活动卡池的简中时间」或「卡池反推的偏移」换算，
因此活动的简中日期一律是**推算值**，不是来源直接给出的值。

## 做规划时的三条口径

1. **收入只能自己填**：主数据里没有任何「每月能攒多少萝卜」的表，活动与大赛的产出也没有可靠的官方数值，
   所以规划只做「你告诉我月收入，我按天折算」这一步，不内置估算。
2. **已确认段优先**：客户端内置排期（`gacha_data`，A 级）比社区预测（C 级）可靠；两者重叠时以客户端为准，
   重叠的行不重复计入消耗。
3. **买不起就记缺口，不扣账**：规划是「站队」而不是模拟真实抽卡，买不起的目标视为放弃，
   把资源留给后面的池子。
