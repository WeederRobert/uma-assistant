## 数据结构

`Data:Course/jian data.json` 是一个数组，每条记录对应一条赛道：

| 字段 | 含义 |
| --- | --- |
| `id` | 赛道 id；前三位与赛场对应（按 `id.json` 观察：101 札幌、102 函馆、103 新潟、104 福岛、105 中山、106 东京、107 中京、108 京都、109 阪神、110 小仓、111 大井、112 隆尚、113 川崎、114 船桥、115 盛冈） |
| `lane` | 分段数组，每段含 `type`（直线 / 弯道）、`name`（直线 / 弯道 / 终弯 / 终直）、`start`、`end`、`length`（单位 m）。`start` / `end` 是赛道上的里程位置，`length = end - start`；首段的 `start` 不一定为 0 |
| `slopes` | 坡道数组，每段含 `start`、`end`、`length`、`slope`；`slope` 只出现 `1` 与 `-1`，页面未说明正负对应的上 / 下坡方向，本目录不推断 |

`Data:Course/jian data.json` 当前有 **107** 条赛道记录，全部能在 `id.json` 中找到名称；`id.json` 另列出 119 条，多出的赛场（川崎、船桥、盛冈、隆尚等）没有出现在这份简中几何数据里。

部分赛道的首段 `start` 大于 0（如 10501 为 300、10506 为 100），段与段之间也可能留有空档（如 10502 从 500 直接跳到 700）。这些空档按位置看都是直线，但源数据没有单独列出，统计口径如下：

- **切线**：首段 `start > 2` 时，0 到首段起点这一段是发走后的开场直线。`races` 模块把它补成一段 `name = 切线`、`inferred = true` 的直线（长度记在 `opening_straight`），**这是推断出来的分段，源数据里没有这一条**。当前 107 条赛道里有 12 条带切线。
- **总长**取最后一段的 `end`；不要用「首段 `start` + 各段 `length` 之和」，否则遇到段间空档会算出与数据库距离不符的假偏差。
- **直线段数**＝`lane` 里显式标为「直线 / 直」的段 **+ 切线**；中段空档仍单列为「未列出长度」，不并进直线段——弯道之间省略的部分同样是直线，但没有位置信息能证明它连续，不补段。
- 与数据库的 `distance` 比较要留 2m 容差（如 11102 大井 1800m 数据页为 1801m）。

引用分段数量时要把这几个口径一起说明。

> 这些是赛道几何，不是比赛数值。以「终直 500m」为例，它只说明最后一段直线的长度，不能直接推出加速区间或最高速度。

## 源数据中的特殊写法与异常值

以下记录保持原样，不修正；引用时需说明这是源数据的写法：

- **10301 新潟 草地 1000m**：直线赛道，`lane` 为两段直线——`直线 0–650`（650m，`length` 记 650）与 `终直 650–1000`（350m），总长 1000m，无空档。早前有资料称这段只有一段「直」，与当前数据页不符。
- **10613 东京 泥地 2400m**：`id.json` 名称为「泥2400」，`lane` 前 7 段正好铺满 0–2400m（末段为「直线 1900–2400」），但第 8 段「弯道」又记 `start` 2348、`end` 2848，与第 7 段重叠 52m 并越过终点 448m；按末段终点算总长为 2848m，与 2400m 不一致，且没有标记「终直」。该记录不适合直接用于分段计数。
- **11102 大井 泥地 1800m / 11103 大井 泥地 2000m / 10907 阪神 草地 2400m**：`lane` 中相邻段存在重叠（分别重叠于第 4、5、2 段），总长仍与数据库距离一致。

## 与结构化数据的关系

- 本文件只收录 6 条高频赛道作为示例，目的是让助手能回答「这条赛道有几段直线 / 坡道」这类几何问题。
- 完整 107 条记录已由 `races` 模块（P3-1a，2026-10-26）结构化入库，由结构化查询回答；不要把整份 JSON 直接放进知识库切块。要查具体某条赛道，用侧栏「赛道」而不要依赖本文件的 6 条示例。
- 赛道几何不能替代比赛数值：最高速度、加速度、耐力消耗与坡道修正公式仍属「已知缺口」；马场状态只有出现率（见 `modules/races` 的「场地状态出现率」卡），没有修正系数。
