# 规划模块（千里眼 / 萝卜规划）

`modules/planner` 回答两件事：**接下来半年有哪些卡池与活动**（千里眼），以及**手上的萝卜够抽哪些**（规划）。
数据来源、口径与限制都写在这里，面板只做展示。

## 数据来源

| 段 | 来源 | 获取方式 | 级别 |
| --- | --- | --- | --- |
| 已确认段 | 本机 `master.mdb` 的 `gacha_data` / `text_data` / `gacha_exchange` / `gacha_available` | `mode=ro` 只读打开，按 `sha256` 判断要不要重新导入 | A（游戏本体数据） |
| 预测卡池 | BWiki SMW：`[[分类:赛马娘卡池]][[简中::未实装]]` 的 `简中开始时间` / `简中结束时间` | 串行 + 1.5 s 间隔 + 6 h TTL 缓存，面板可强制刷新 | C（wiki 自己算好的简中预测时间） |
| 活动 | BWiki SMW：`[[分类:活动]]`（`名称` / `开始描述` / `结束描述` / `类型`） | 同上；**只有日服时间**，简中时间靠卡池反推的偏移换算 | C（推算） |

`简中::未实装` 是 BWiki 自己的标记：页面「预测卡池」表用的就是

```
[[分类:赛马娘卡池]][[简中::未实装]]|?简中开始时间|?简中结束时间
```

即「日服已经上线、简中还没实装」的卡池，页面直接把简中预测时间写在属性里。本项目只读这一层，
不去抓日服 / 繁中服的排期（跨服进度不同步，抓回来只会被误当成简中日程）。

## 为什么活动要用「偏移」

BWiki 的活动表只有日服时间，简中服没有对应的活动分类。要让活动出现在简中日程里，只能从卡池反推：

1. 预测卡池页每一条同时带**日服** `开始描述` 与**简中** `简中开始时间`，两条相减就是那个时间点的偏移；
2. 2026-11-01 实测 136 组卡池，偏移 **1104 天**且完全一致（`spread = 1104~1104`）；
3. 活动标题能对上同名「活动卡池」时（如 `剧情活动「寂寥秋色，连缀思念」` ↔ `「寂寥秋色，连缀思念」活动卡池`），
   直接用卡池的简中时间（`basis = 活动卡池`）；对不上的用偏移换算（`basis = 偏移推算`），日服结束时间同样换算。

**不抄 wiki 页面上写的「-185 天 / +423 天」这类调整记录**：那是某一时期的账，会随简中服追进度而变化。
这里每次刷新都用当期数据重新算，并在相邻两点之间线性插值，偏移一旦变化会自动跟着变。

## 分段：避免同一期被算两次

| `segment` | 含义 | 进规划 |
| --- | --- | --- |
| `confirmed` | `master.mdb` 里进行中或未来的普通池（排除常驻池与未定档占位） | ✅ |
| `predicted` | BWiki 预测，且开始时间**晚于** mdb 已确认段的最后一刻（`horizon`） | ✅ |
| `overlap` | BWiki 预测，但落在 mdb 已确认段之内 —— 同一期卡池的两种描述 | ❌ 只展示 |

`horizon` = 已确认段里最晚的结束时间（当前快照 2027-01-26 11:59）。半年窗口里，
这一段之前看 mdb，之后看 wiki 预测。

## 口径

| 项 | 口径 | 依据 |
| --- | --- | --- |
| 单抽成本 | `gacha_data.cost_single`（实测 150） | mdb 真实列 |
| 天井抽数 | `gacha_exchange.pay_item_num`（兑换本期 UP 卡需要的点数，实测 200） | mdb 真实列 |
| 天井萝卜 | 天井抽数 × 单抽成本 = 200 × 150 = 30000 | 上两列相乘；**「1 抽 = 1 点」这条规则不在 mdb 里**，见「已知限制」 |
| 预测池成本 | 取已确认段里出现最多的 `cost_single` / `ceiling_pulls`（众数） | 预测池不在 mdb 里，只能借当期口径 |
| 萝卜收入 | **用户自己填**的每月收入，按 30 天/月线性折算到每个目标池开始那天 | 库里没有任何收入数据，不估算、不外推 |
| 抽券 | 1 张 = 1 抽，优先于萝卜使用 | 用户输入，不区分有偿 / 无偿 |
| 买不起的目标 | 标「缺口」且**不扣账**（视为放弃，把萝卜留给后面的池子） | 否则会连带惩罚后面的池子 |

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/planner/status` | 条数、mdb 是否过期、偏移、成本口径、窗口天数 |
| GET | `/api/planner/forecast?days=180&include_overlap=true` | 千里眼窗口：`pools`（含 `segment`）、`events`、`offset`、`cost`、`counts`、`notes` |
| POST | `/api/planner/refresh` | body `{"force": true}`：重新导入 mdb 已确认段并重抓两条 BWiki 来源 |
| GET | `/api/planner/plans` | 已存方案列表 |
| POST | `/api/planner/plans` | 新建方案（`name` / `carats` / `tickets` / `monthly_income` / `targets`） |
| GET | `/api/planner/plans/{id}` | 方案 + 用它当前预测现算的评价（404 表示没有这个方案） |
| PUT | `/api/planner/plans/{id}` | 覆盖保存 |
| DELETE | `/api/planner/plans/{id}` | 删除 |
| POST | `/api/planner/evaluate` | 不落库的试算，body 同方案 |

`pools` 每条都带 `segment` / `segment_label` / `starts_local` / `ends_local` / `days_to_start` /
`days_left` / `cost_single` / `ceiling_pulls` / `ceiling_carats` / `source_level` / `source_url` /
`jp_starts_local` / `offset_days`，预测行另带日服原时间与偏移天数。时间一律按运行环境的系统时区换算。

## 面板

侧栏「规划」，两张卡：

| 卡 | 内容 |
| --- | --- |
| 千里眼：近半年预测 | 窗口（60 / 90 / 180 / 365 天）+「刷新预测」；三段列表（已确认卡池 / 预测卡池 / 活动），每行可勾选；与 mdb 重叠的预测行折在 `<details>` 里；底部「口径与限制」直接来自接口的 `notes` |
| 钻石（萝卜）规划 | 当前萝卜 / 抽券 / 每月收入 + 目标池（勾选后列出，可改抽数）+「试算」/「保存方案」/「重置」；结果显示够不够、缺口、期间收入与期末结余 |
| 已存方案 | 加载 / 删除多套方案，加载后立即按当前预测重算 |

## 已知限制

- **「1 抽 = 1 点」这条换算规则不在 mdb 里**：`gacha_exchange.pay_item_num` 只给「兑换 Up 卡需要的点数」，
  点数怎么积累（是否 1 抽 1 点）由游戏规则决定，本项目没有可核对的来源，因此天井萝卜是**按 1 抽 1 点算的**，
  面板上写明这一点。
- **预测段不是官方公告**：`简中开始时间` 由 wiki 志愿者按日服节奏推算，游戏方临时改排期时会对不上；C 级。
- **活动只能推算**：活动表本身没有简中时间，靠同名活动卡池或卡池偏移换算；主题卡池与活动不同步时（提前或延后）会有几天误差。
- **偏移是全局单一来源**：所有活动共用一套「日服 → 简中」映射。如果简中服按活动类型分开调进度，这里看不出来。
- **不预测未公布的池子**：只回显 wiki 已经写出来的行；没有对应页面就没有行，不用空档去「推断」下一期。
- **常驻池与未定档不参与**：`2050-01-01` 结束的常驻池、开始时间落在 2049/2050 的未定档占位都不进千里眼，数量在导入日志里。
- **收入完全靠用户**：不内置任何「每月能攒多少萝卜」的估算，也不从活动/大赛反推收益。
